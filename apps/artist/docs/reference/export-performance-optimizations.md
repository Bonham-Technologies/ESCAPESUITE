# Export Performance Optimizations (`src/core/exportMP4.ts`, `src/core/exportWebM.ts`, `src/core/frameSource.ts`, `src/core/frameManager.ts`)
The export pipeline includes several optimizations to improve performance:
- **Background tab export (MP4)**: Uses WebCodecs `VideoDecoder` in a Web Worker for frame decoding, enabling full-speed exports even when the browser tab is in the background. Web Workers are not subject to browser throttling that affects `setTimeout` and `video.play()` on the main thread. (ESCSUITE-254: before this, the worker threw on every source and the export silently decoded in the page — see "Video Decode Worker".)
- **FrameSource abstraction**: `frameSource.ts` provides a unified interface for frame fetching with automatic fallback:
  - `WebCodecsFrameSource`: Uses `VideoDecodeManager` for H.264 MP4 files (background-capable), wrapped so a frame the worker fails mid-export hands the source to `<video>`
  - `HTMLVideoFrameSource`: Falls back to `<video>` element seeking for WebM, a source the worker refuses, or unsupported browsers — reported through `createSource`'s `onFallback`, which the MP4 exporter turns into its once-per-export "Decoding in the page" line. **One element per slot** (ESCSUITE-313): `getFrame(timestamp, slot)` serves slot 0 from the element the source was created with and slot k from a k-th element over the same object URL, made the first time it is asked for and disposed with the source; `exportMP4.ts`'s frame loop passes each clip's slot from the same `assignElementSlots` the element exporters use, through `getFrameAtTime(manager, sourceId, time, slot)`, so two clips of one source in one frame each hold their own frame until the draw. A further element that will not load is warned about once and its slot answers `null` from then on — the clip is left out, silently, for the rest of the export. `FailoverFrameSource` passes the slot to both sides; the worker ignores it (it answers each request on its own). `drawTransition` takes each side's `<video>` from its caller, so every caller resolves the two sides by slot. Chosen over returning a detached `new VideoFrame(video)` per request because that would cost one `VideoFrame` per fallback frame of every in-page export — every ESCAPECRAFT WebM recording — where this costs a second element only when two clips of one source overlap. It carries the same wedge guard as the element exporters, under the same rule (ESCSUITE-305, `core/seekWedge.ts`), counted per element — slot 0 and each further slot on its own: the count resets when a request starts over an element no longer `seeking`, and after the request's waits it resets for a seek that landed or a frame to draw, adds one for an element still `seeking` with `readyState < 2`, and is otherwise left. A request that needs no seek (its time is within the tolerance) but finds the element still `seeking` from an earlier one gets the **same waits a seek does** — the 500 ms `'seeked'` wait and the 100 ms readiness wait — before it is counted (re-review round 1), so a slow seek is not refused by the requests held at its time (an incoming transition clip, or the outgoing one fetched twice a frame), while a wedged one still is; the third in a row throws `SourceNotSeekableError` by the source's name (`createSource` / `loadFrameSource` take it, `exportMP4.ts` passes `SourceVideo.name`). `getFrameAtTime` (`frameManager.ts`) rethrows that one error instead of warning and skipping the clip, and `FailoverFrameSource` does not swallow it either: the `<video>` a worker source was handed to is the last path there is, so a source that wedges there fails the export by name. Because a fetch can now reject, `exportMP4.ts` gathers the regular clips' frame fetches into one `Promise.all` before it awaits the transition fetches, and marks that promise handled, so a fetch that fails while a transition fetch is awaited (or after one already threw) leaves no unhandled rejection; the `await` of it still rethrows the first failure. Its load has a deadline (ESCSUITE-325): `create`, each further slot's element and `loadVideoElement` share `waitForVideoLoad` (`core/exportTypes.ts`), which arms `METADATA_LOAD_TIMEOUT_MS` (15 s, from `videoProcessor.ts`, the one constant) when the listeners attach and clears it on `loadeddata`, `error` and expiry. A source the browser neither decodes nor rejects used to park the export at "Loading media files…" for ever; now the element is torn down (handlers detached, `src` removed, `load()`, URL revoked) and the wait rejects with a `MediaLoadTimeoutError` — "Could not read <id> — the browser did not report its metadata within 15 s" (the id, since `create` is only handed the id). `exportMP4` turns that one error into an `ExportError` that fails the export by name, releasing what it had loaded, because skipping would drop the clip from the file without a word; every other load failure (an `error` event) is still warned about and skipped. That is slot 0's load; a further slot's element that times out is not an `ExportError` — it is handled as any further element that will not load (warned once, the slot answers `null`, the clip left out), and its timeout does not revoke the URL slot 0 still reads
- **Frame tolerance**: `HTMLVideoFrameSource.getFrame()` skips the seek only when the request is within half a frame of the element's current time: `seekToleranceFor(frameRate)` = `0.5 / max(frameRate, 30)` (ESCSUITE-263). The old rule was a strict `> 1/30`, and because the export's requests are one 1/30 frame apart the float difference often came out just under it, so about every other frame of an in-page MP4 export (every ESCAPECRAFT WebM recording, Safari, any source the worker refuses) was a repeat of the previous one; that is fixed. The floor at 30 keeps the window under the request spacing for a low-rate source, and a missing or non-finite rate counts as 30. An imported video's rate is measured at import since ESCSUITE-276 (`frameRateSource: 'measured'`, so a 120 fps file gets a 1/240 s window — `frameSource.measuredRate.test.ts`); a rate that could not be measured, an ESCAPECRAFT take (`'configured'`, 30) and every source imported before then still read 30, a 1/60 s window. The rate is threaded `exportMP4` -> `loadFrameSource` -> `createSource` -> `HTMLVideoFrameSource` (also on the failover path)
- **Seek target (ESCSUITE-265, ESCSUITE-495)**: both element paths — `HTMLVideoFrameSource.getFrame()` (MP4) and `elementFrames.ts`'s `syncVideoToTime` (WebM, GIF) — seek to `elementSeekTarget(time)` = `time + ELEMENT_SEEK_BIAS` (1 ms since ESCSUITE-495, 0.1 ms before; `core/elementSeek.ts`), not to `time` itself. The element shows the frame whose *stored* start is at or before the seek, and two roundings can put that start just after the frame's nominal one, where the request lands: the engine's microsecond (below) and the container's millisecond (the next bullet). An export's requests are frame-aligned (`clip.startTime + n / 30`), so most land exactly on a source frame's start, and a 30 fps frame starts 33333.33… µs after the last. Both measured engines resolve a seek at microsecond precision and land one short of the frame on a third of those starts, showing the frame before it: Chromium 153 on the starts whose fraction is .67 (it truncates the request — `currentTime` reads back 1.066666 for 1.0666…67), Firefox 155 on the .33 ones. Measured with a per-frame-coloured 30 fps source: 20 of 60 frames one early in each engine at bias 0, none at 1 µs, 10 µs or 0.1 ms; through the app's own trimmed MP4 export, 15 of 45 in each engine before and 0 after, and the WebM export 15 of 45 → 0 in Chromium. Waiting longer does not help — after `seeked`, after `requestVideoFrameCallback` and after a further 100 ms the picture is the same, and Firefox's rVFC `mediaTime` echoes the request rather than the frame drawn, so nothing an element reports can detect it. The 0.1 ms bias was a hundred times that measured margin. At 0.1 ms it changed neither seek count (the skip windows are 1/60 s on the MP4 path and 0.4 of an output frame on the element exporters, both far wider) nor any perf ceiling. At 1 ms (ESCSUITE-495) one narrow case moves: the element rests 1 ms past its last request, so a clip slowed to about 0.40-0.43x (element exporters) or 0.50-0.53x (MP4 element path) in a 30 fps export can skip a seek it used to issue, within the staleness those skip windows already allow just below those speeds. Pinned by `frameSource.boundarySeek.test.ts` (a `<video>` double reproducing each engine's measured rounding, 30 and 60 fps sources, from 0 and from a 0.5 s trim) and `elementFrames.test.ts`. The preview's own seeks (`usePreviewRenderLoop.ts`) are separate and unchanged: they skip anything within 0.05 s, so the paused preview is not frame-accurate to begin with
- **Millisecond timecodes (ESCSUITE-495)**: a WebM (Matroska) timecode holds whole milliseconds, so every frame start is stored rounded to the nearest one — at most half a millisecond late. A 30 fps frame at 66.67 ms is stored at 67 ms, so every third frame of a 30 fps WebM on a fixed grid is stored a third of a millisecond late. An ESCAPECRAFT take is a 30 fps WebM too; its timestamps are capture times stored as whole milliseconds, so a frame captured just before a requested time can be stored just after it in the same way. A 0.1 ms bias landed short of those and the element showed the frame before: a 30 fps barcode source (`apps/e2e/fixtures/presented-frame/frame-barcode-30fps.webm`) exported with 18 wrong frames in Chromium, every run, each a late-stored frame replaced by the one before. The bias is now 1 ms: twice the most a rounded timecode can be late, and a thousand times the engine's microsecond. It is a shift, not a snap to the middle of a source frame: the element path cannot know where a source's frames start (a take's timestamps are its capture times, not a fixed grid), the middle of an *output* frame would choose different source frames than the decode worker does for the same request, and a shift keeps the decode worker's rule — the last frame that starts at or before the request, within a tolerance (`TIME_TOLERANCE_US`, `workers/frameDecoder.ts`, 0.5 ms; an MP4 with millisecond timestamps is late by no more than that). So a request that is not on a frame start, from a trim or a source whose frames are off the timeline's grid, moves 1 ms, and one within 1 ms before a frame's stored start is treated as that frame. The worker's tolerance is half that, so a request 0.5-1 ms before a frame's start is the one place the two paths disagree: the worker shows the frame before, the element the frame itself — a neighbouring frame, about a millisecond apart in time, reached only off the timeline's grid (a trim or a source rate other than the export's); widening `TIME_TOLERANCE_US` to 1 ms would align them. At under a quarter of a frame at 240 fps, the bias cannot carry a request on one frame's start past the next frame's, even with that one stored half a millisecond early. It changes neither seek count (the element sits 1 ms past its last request, inside the 1/60 s skip window on the MP4 path — half a frame of the source's measured rate, 2.1 ms at 240 fps — and the 0.4-output-frame one on the element exporters) nor any perf ceiling. Pinned by `frameSource.boundarySeek.test.ts` (each engine's double also reading millisecond timecodes, ten source rates from 23.976 to 240 fps, requests on a frame start, half way in and 2 ms before the next) and `apps/e2e/tests/regressions/ESCSUITE-495.spec.ts`. The preview's seeks are unchanged: they carry no bias at all and skip anything within 0.05 s, so the paused preview is not frame-accurate to begin with, and the headless render shares the exporters' code, so it has the fix too.
- **Presented frame (ESCSUITE-454)**: both element paths also wait, after `'seeked'`, for the sought frame to be presented (`core/presentedFrame.ts`). Chromium can fire `'seeked'` with `seeking` false and `readyState` 4 while the frame `drawImage` paints is still the one from before the seek, so an export sometimes held the previous frame (in CI: the untrimmed start at a trimmed clip's frame 0, MAD 70.9; source frame 7 at frame 8, 42.7), while the worker export of the same project was right. Each seek an export issues registers a `requestVideoFrameCallback` immediately before assigning `currentTime`; once the seek has landed, the request waits for that callback, at most `PRESENTED_FRAME_WAIT_MS` (500 ms, the same as the `'seeked'` wait, well inside the 2 s wedge grace) — a ceiling, not a delay. Where no callback comes the request draws on `'seeked'`, as before: an element without `requestVideoFrameCallback` (feature detection); any request in a hidden document (it presents nothing, and nothing is registered or counted); and an element whose landed seeks go `MISSED_PRESENTATIONS_LIMIT` (2) times in a row without a callback inside the ceiling — whether WebKit answers one after a paused seek is unmeasured — for the rest of the export, at a one-off cost of two ceilings. A callback that arrives starts that count again. An element that misses `MISSED_PRESENTATIONS_BUDGET` (4) times in all, hits in between or not, is drawn on `'seeked'` from then on too: an engine that presented only when the picture changes would answer every other seek of a 15 fps source in a 30 fps export, which the in-a-row rule never catches, and pay the ceiling every other frame (about 7.5 minutes on a 60 s export); the budget caps it at four ceilings. A seek that never landed cancels its callback and counts nothing; the wedge count handles it. Nor does a seek that lands where the element already was (a request past the source's end lands on the end): Chromium presents no frame for it (measured, Chromium 1243), and the element already shows that frame, so it is neither waited for nor counted as a miss. The `'seeked'` and wedge semantics (`landed`, `landedPromptly`) are unchanged. Pinned by `frameSource.presentedFrame.test.ts` and `elementFrames.presentedFrame.test.ts` (a `<video>` double, `test/doubles/presentingVideo.ts`, that presents the sought frame 40 ms after `'seeked'`), and end to end by `apps/e2e/tests/regressions/ESCSUITE-454.spec.ts` (ESCSUITE-479): a WebM export of a frame-numbered source cut into 120 pieces, every frame read back; with the wait removed, 10 of 10 Chromium runs wrote 2-20 stale frames
- **Encoder backpressure**: MP4's loop waits while `videoEncoder.encodeQueueSize > 5`, paired with
  the 30-second backpressure timeout below; WebM's own loop waits above `> 20`. Both exist to
  prevent memory exhaustion
- **Decoded frame ownership (`frameManager.ts`, ESCSUITE-123)**: every `VideoFrame` `getFrameAtTime`
  fetches is tracked in `currentFrames` — a `Set`, not a map keyed by `${sourceId}:${timestamp}` —
  and `cleanupIterationFrames` closes every one of them once the export frame is drawn. The key used
  to collide: a whole-clip transition's outgoing clip is fetched once as an ordinary active clip and
  again as the transition's own outgoing side, at the bit-identical source time, and each fetch is a
  distinct decoded frame (the decode worker hands back a fresh `frame.clone()` per request). A
  string-keyed map silently dropped the first fetch, leaking a full decoded frame per frame of every
  transition; the `Set` keeps and closes both.
