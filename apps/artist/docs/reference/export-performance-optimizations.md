# Export Performance Optimizations (`src/core/exportMP4.ts`, `src/core/exportWebM.ts`, `src/core/frameSource.ts`, `src/core/frameManager.ts`)
The export pipeline includes several optimizations to improve performance:
- **Background tab export (MP4)**: Uses WebCodecs `VideoDecoder` in a Web Worker for frame decoding, enabling full-speed exports even when the browser tab is in the background. Web Workers are not subject to browser throttling that affects `setTimeout` and `video.play()` on the main thread. (ESCSUITE-254: before this, the worker threw on every source and the export silently decoded in the page — see "Video Decode Worker".)
- **FrameSource abstraction**: `frameSource.ts` provides a unified interface for frame fetching with automatic fallback:
  - `WebCodecsFrameSource`: Uses `VideoDecodeManager` for H.264 MP4 files (background-capable), wrapped so a frame the worker fails mid-export hands the source to `<video>`
  - `HTMLVideoFrameSource`: Falls back to `<video>` element seeking for WebM, a source the worker refuses, or unsupported browsers — reported through `createSource`'s `onFallback`, which the MP4 exporter turns into its once-per-export "Decoding in the page" line. **One element per slot** (ESCSUITE-313): `getFrame(timestamp, slot)` serves slot 0 from the element the source was created with and slot k from a k-th element over the same object URL, made the first time it is asked for and disposed with the source; `exportMP4.ts`'s frame loop passes each clip's slot from the same `assignElementSlots` the element exporters use, through `getFrameAtTime(manager, sourceId, time, slot)`, so two clips of one source in one frame each hold their own frame until the draw. A further element that will not load is warned about once and its slot answers `null` from then on — the clip is left out, silently, for the rest of the export. `FailoverFrameSource` passes the slot to both sides; the worker ignores it (it answers each request on its own). `drawTransition` takes each side's `<video>` from its caller, so every caller resolves the two sides by slot. Chosen over returning a detached `new VideoFrame(video)` per request because that would cost one `VideoFrame` per fallback frame of every in-page export — every ESCAPECRAFT WebM recording — where this costs a second element only when two clips of one source overlap. It carries the same wedge guard as the element exporters, under the same rule (ESCSUITE-305, `core/seekWedge.ts`), counted per element — slot 0 and each further slot on its own: the count resets when a request starts over an element no longer `seeking`, and after the request's waits it resets for a seek that landed or a frame to draw, adds one for an element still `seeking` with `readyState < 2`, and is otherwise left. A request that needs no seek (its time is within the tolerance) but finds the element still `seeking` from an earlier one gets the **same waits a seek does** — the 500 ms `'seeked'` wait and the 100 ms readiness wait — before it is counted (re-review round 1), so a slow seek is not refused by the requests held at its time (an incoming transition clip, or the outgoing one fetched twice a frame), while a wedged one still is; the third in a row throws `SourceNotSeekableError` by the source's name (`createSource` / `loadFrameSource` take it, `exportMP4.ts` passes `SourceVideo.name`). `getFrameAtTime` (`frameManager.ts`) rethrows that one error instead of warning and skipping the clip, and `FailoverFrameSource` does not swallow it either: the `<video>` a worker source was handed to is the last path there is, so a source that wedges there fails the export by name. Because a fetch can now reject, `exportMP4.ts` gathers the regular clips' frame fetches into one `Promise.all` before it awaits the transition fetches, and marks that promise handled, so a fetch that fails while a transition fetch is awaited (or after one already threw) leaves no unhandled rejection; the `await` of it still rethrows the first failure. Its load has a deadline (ESCSUITE-325): `create`, each further slot's element and `loadVideoElement` share `waitForVideoLoad` (`core/exportTypes.ts`), which arms `METADATA_LOAD_TIMEOUT_MS` (15 s, from `videoProcessor.ts`, the one constant) when the listeners attach and clears it on `loadeddata`, `error` and expiry. A source the browser neither decodes nor rejects used to park the export at "Loading media files…" for ever; now the element is torn down (handlers detached, `src` removed, `load()`, URL revoked) and the wait rejects with a `MediaLoadTimeoutError` — "Could not read <id> — the browser did not report its metadata within 15 s" (the id, since `create` is only handed the id). `exportMP4` turns that one error into an `ExportError` that fails the export by name, releasing what it had loaded, because skipping would drop the clip from the file without a word; every other load failure (an `error` event) is still warned about and skipped. That is slot 0's load; a further slot's element that times out is not an `ExportError` — it is handled as any further element that will not load (warned once, the slot answers `null`, the clip left out), and its timeout does not revoke the URL slot 0 still reads
- **Frame tolerance**: `HTMLVideoFrameSource.getFrame()` skips the seek only when the request is within half a frame of the element's current time: `seekToleranceFor(frameRate)` = `0.5 / max(frameRate, 30)` (ESCSUITE-263). The old rule was a strict `> 1/30`, and because the export's requests are one 1/30 frame apart the float difference often came out just under it, so about every other frame of an in-page MP4 export (every ESCAPECRAFT WebM recording, Safari, any source the worker refuses) was a repeat of the previous one; that is fixed. The floor at 30 keeps the window under the request spacing for a low-rate source, and a missing or non-finite rate counts as 30. An imported video's rate is measured at import since ESCSUITE-276 (`frameRateSource: 'measured'`, so a 120 fps file gets a 1/240 s window — `frameSource.measuredRate.test.ts`); a rate that could not be measured, an ESCAPECRAFT take (`'configured'`, 30) and every source imported before then still read 30, a 1/60 s window. The rate is threaded `exportMP4` -> `loadFrameSource` -> `createSource` -> `HTMLVideoFrameSource` (also on the failover path)
- **Seek target (ESCSUITE-265)**: both element paths — `HTMLVideoFrameSource.getFrame()` (MP4) and `elementFrames.ts`'s `syncVideoToTime` (WebM, GIF) — seek to `elementSeekTarget(time)` = `time + ELEMENT_SEEK_BIAS` (0.1 ms, `core/elementSeek.ts`), not to `time` itself. An export's requests are frame-aligned (`clip.startTime + n / 30`), so most land exactly on a source frame's start, and a 30 fps frame starts 33333.33… µs after the last. Both measured engines resolve a seek at microsecond precision and land one short of the frame on a third of those starts, showing the frame before it: Chromium 153 on the starts whose fraction is .67 (it truncates the request — `currentTime` reads back 1.066666 for 1.0666…67), Firefox 155 on the .33 ones. Measured with a per-frame-coloured 30 fps source: 20 of 60 frames one early in each engine at bias 0, none at 1 µs, 10 µs or 0.1 ms; through the app's own trimmed MP4 export, 15 of 45 in each engine before and 0 after, and the WebM export 15 of 45 → 0 in Chromium. Waiting longer does not help — after `seeked`, after `requestVideoFrameCallback` and after a further 100 ms the picture is the same, and Firefox's rVFC `mediaTime` echoes the request rather than the frame drawn, so nothing an element reports can detect it. The bias is a hundred times the measured margin and a fortieth of a frame at 240 fps. A request that is not on a frame start moves 0.1 ms, so a time within 0.1 ms before a frame's start is treated as that frame — the convention the decode worker already applies within 0.5 ms (`TIME_TOLERANCE_US`, `workers/frameDecoder.ts`), only narrower. It changes neither seek count (the skip windows are 1/60 s on the MP4 path and 0.4 of an output frame on the element exporters, both far wider) nor any perf ceiling. Pinned by `frameSource.boundarySeek.test.ts` (a `<video>` double reproducing each engine's measured rounding, 30 and 60 fps sources, from 0 and from a 0.5 s trim) and `elementFrames.test.ts`. The preview's own seeks (`usePreviewRenderLoop.ts`) are separate and unchanged: they skip anything within 0.05 s, so the paused preview is not frame-accurate to begin with
- **Encoder backpressure**: MP4's loop waits while `videoEncoder.encodeQueueSize > 5`, paired with
  the 30-second backpressure timeout below; WebM's own loop waits above `> 20`. Both exist to
  prevent memory exhaustion
- **Decoded frame ownership (`frameManager.ts`, ESCSUITE-123)**: every `VideoFrame` `getFrameAtTime`
  fetches is tracked in `currentFrames` — a `Set`, not a map keyed by `${sourceId}:${timestamp}` —
  and `cleanupIterationFrames` closes every one of them once the export frame is drawn. The key used
  to collide: a whole-clip transition's outgoing clip is fetched once as an ordinary active clip and
  again as the transition's own outgoing side, at the bit-identical source time, and each fetch is a
  distinct decoded frame (the decode worker hands back a fresh `frame.clone()` per request). A
  string-keyed map silently dropped the first fetch, leaking a full decoded frame per frame of every
  transition; the `Set` keeps and closes both.
