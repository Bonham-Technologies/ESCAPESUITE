## Task 1 — ESCSUITE-54: the compositor draws 30 frames a second, not 23

**What is wrong:** `Compositor.render` (`apps/craft/src/core/compositor.ts`) gates on
`now - lastFrameTime < 1000 / targetFrameRate` and snaps `lastFrameTime = now`. `1000/30` is
exactly `2 * (1000/60)` in IEEE 754, so two 60 Hz animation frames meet the gate with zero
margin: any jitter below the ideal refuses the second tick and the draw waits for a third
(50 ms). Measured: 22.4–22.8 composited fps on the Mac, 23.11 on the CI runner, 2.63 rAF per
composited frame.

**The fix — a deadline gate with a tolerance and a catch-up clamp:**

```ts
// Fields: replace lastFrameTime with
private nextFrameDue = 0;
/** How early a tick may run a frame that is due on the next tick. Well under one
 *  60 Hz tick (16.7 ms), so two consecutive ticks can never both qualify. */
private static readonly FRAME_TOLERANCE_MS = 4;

private render = (): void => {
  this.animationFrameId = requestAnimationFrame(this.render);
  const now = performance.now();
  if (now < this.nextFrameDue - Compositor.FRAME_TOLERANCE_MS) return;
  const frameInterval = 1000 / this.targetFrameRate;
  // Advance on the schedule, not from `now`, so jitter does not accumulate; but a
  // stall longer than a frame (a hidden tab, a GC pause) resyncs to now instead of
  // drawing a burst to catch up.
  this.nextFrameDue = now - this.nextFrameDue > frameInterval ? now + frameInterval : this.nextFrameDue + frameInterval;
  this.drawFrame();
};
```

`start()` sets `nextFrameDue = 0` so the first render draws immediately (as today).

**Tests, red first** (`compositor.test.ts` "render loop throttling" describe; `now` is the scripted
`performance.now()`, `tickAnimationFrames()` drives the rAF double):
- **jittered 60 Hz ticks still give 30 draws a second** — 60 ticks whose spacing alternates
  16.67 − 0.5 and 16.67 + 0.5 ms (mean 16.67); expect exactly 30 draws after `start()`'s one.
  Against the old gate this yields fewer (record the number).
- **two consecutive ticks never both draw** — with ticks exactly 16.667 ms apart, no two adjacent
  ticks draw (the tolerance is safe).
- **a stall does not burst** — draw, then no ticks for 500 ms, then ticks every 16.67 ms: the
  first tick after the stall draws, the next does not, and the following draws (one per ~33 ms),
  never two in a row.
- The three existing throttle tests stay byte-identical and pass (check: start draws; +10 skip;
  +30 draw; 10 fps: +50 skip, +60 draw; rescheduling).
- `compositor.perf.test.ts` "never draws more often than the target frame rate" (60 exact ticks →
  `TARGET_FPS + 1`) must still hold exactly.

**Benchmark evidence (constraint 6):** `pnpm --filter @escapesuite/e2e exec playwright test
--config=playwright.perf.config.ts craft-recording` reports `craft-pip-recording`'s

## Task 2 — ESCSUITE-57: the save guard refuses a non-finite duration (same branch, own commit)

**What is actually true:** CRAFT's `core/thumbnailGenerator.ts` `extractVideoMetadata` already
maps a non-finite or zero `video.duration` to `knownDuration || 0`, so the real save path never
hands `useRecordingSave` an `Infinity`. The ticket over-states the bug. Harden the guard anyway,
because the hook's contract should not depend on a helper it does not own:
`apps/craft/src/hooks/useRecordingSave.ts` — `metadata.duration > 0` becomes
`Number.isFinite(metadata.duration) && metadata.duration > 0`, falling back to
`recordedDuration` as today. **Red first** in `useRecordingSave.test.ts`: the thumbnail module
mock resolves `{ duration: Infinity, … }` and the stored `duration` must be the recorded one
(mirror the existing "falls back to the timed duration when the file reports none" test).
Comment on the guard: why both halves. Update the Jira ticket's premise in the PR body (the
controller carries it to Jira).

## Task 3 — ESCSUITE-56: `extractAudioMetadata` gets the same seek-to-end probe

`apps/artist/src/core/videoProcessor.ts` `extractAudioMetadata` resolves with `audio.duration`
unchecked, so a headerless audio file (raw MediaRecorder WebM/Opus) builds an infinitely long
audio clip. No hang — the audio path never seeks — but the same wrong length.

- **Extract the probe once**: a private helper, e.g.
  `loadMediaDuration(element: HTMLMediaElement, objectUrl: string, name: string, kind: 'video' | 'audio'): Promise<number>`
  (name it well; the exact signature is yours) that owns `loadedmetadata` → usable-or-probe,
  `durationchange`/`seeked` → first usable value (`duration`, else `currentTime` strictly below
  `END_SEEK_TARGET`), the 5 s timeout → `Could not determine the duration of <name>`, `error` →
  `Failed to load <kind>: <name>`, and the single-release teardown. `extractVideoMetadata` calls
  it and builds its `SourceVideo` from the result — **a pure move for the video half: every
  existing video test byte-unchanged and green**, and the `videoProcessor.ts` branch count for
  the video path unchanged (say what it was and is).
- `extractAudioMetadata` calls the same helper; its `SourceVideo` shape is unchanged.
- **Double:** `apps/artist/src/test/doubles/media.ts` `makeAudio` gains the same `currentTime`
  setter semantics as `makeVideo` (`durationAfterSeek`, `durationStaysUnknown`, `stallSeek`, the
  WebIDL `TypeError` on non-finite) — share the setter between the two makers rather than copy
  it; `AudioScript` gains the fields; document them in the header.
- **Tests, red first**: audio `Infinity` → `durationAfterSeek`; audio `0` → same; audio
  `Infinity` + `stallSeek` → rejects after 5 s (fake timers); finite audio → no seek
  (`media.seeks` empty); URL revoked exactly once on success/timeout/error for audio; the
