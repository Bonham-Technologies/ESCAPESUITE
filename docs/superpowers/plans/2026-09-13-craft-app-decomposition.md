# CRAFT App decomposition (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Split `apps/craft/src/App.tsx` (1,315 lines: one component holding the whole recorder — capability detection, stream acquisition, PiP compositing, the recorder's five callbacks, countdown and duration tickers, save-to-IndexedDB, the recordings library with playback/download/delete/send-to-editor, window keyboard shortcuts, the unmount teardown, ~525 lines of JSX from line 672, and 12 inline icon components from line 1204) into focused modules with **no behaviour change**, the way `Timeline` was split (#342) and `PreviewPlayer` before it (#331). The contract is the existing App suite — `App.settings.test.tsx`, `App.recording.test.tsx`, `App.saving.test.tsx`, `App.library.test.tsx`, 79 tests — passing **byte-unchanged**: no import path in them even needs to move, because `App.tsx` stays at `src/App.tsx` and every `vi.mock` target stays where it is. Each task's reviewer diffs every moved block against the original.

**Current structure (2026-09-12 lines):**

*Store + refs + state (26–69)* — one destructured `useRecorderStore()` call taking 9 slices and 11 actions (26–46); refs `recorderRef`, `recorderTypeRef`, `compositorRef`, `previewRef` (the `<video>`), `canvasPreviewRef` (the PiP `<div>`), `durationIntervalRef`, `countdownIntervalRef`, `capturedThumbnailRef`, `cancelledRef` (56–59, with the comment explaining the late-flush chunk), `micStreamRef` (60–63, with the comment explaining why the mic stream is not in the store) (48–63); state `previewStream`, `isPiPActive`, `playbackUrl`, `playbackName`, `playbackDuration`, `showHelpModal` (64–69).

*Thumbnail capture (72–125)* — `capturePreviewThumbnail` `useCallback([])`: compositor canvas first (`getCanvas()`, `width > 0`, 320×180, `toBlob('image/jpeg', 0.8)`), **falling through to the video element when there is no 2D context or `drawImage` throws**, then the video path (`videoWidth === 0` → `resolve(null)`; no ctx → `resolve(null)`; throw → `resolve(null)`).

## Smells to carry (do not fix)
- **The `App.library.test.tsx` flake.** `it('opens the player for the chosen recording and closes it again')` clicks `Play Standup Demo` and then calls `screen.getByRole('dialog')` synchronously. `handlePlayRecording` is `async` and awaits `getVideoBlob(id)` through `fake-indexeddb`, which settles on a real macrotask that `userEvent`'s await does not cover, so under CI load the dialog is not in the DOM yet and the query times out. The same shape appears in the other four playback tests and in the download tests. The fix is `await screen.findByRole('dialog')` or a `flush()` after the click — **but that edits a pre-existing App test, which this plan forbids**. Moving the handler into `useRecordingLibrary` changes none of the timing; record it as a known flake and leave the tests alone. *(Controller note 2026-09-13: fixed separately on main before this plan runs, so the "byte-unchanged" baseline is the fixed file.)*
- Five library handlers (`handleDeleteRecording`, `handleSendToEditor`, `handlePlayRecording`, `handleClosePlayback`, `handleDownload`) and `toggleSource`/`formatDuration` are recreated on every render while everything else is `useCallback`. Keep the asymmetry: memoising them now would change child re-render behaviour.
- `handleClosePlayback` clears `playbackUrl` and `playbackName` but leaves `playbackDuration` standing until the next play.
- A failed save is logged twice — once by `saveRecording`'s own catch and once by the `.catch` on its call in `onStop`.
- Effect 3's deps are `[previewStream]` while its body reads `compositorRef.current` and `canvasPreviewRef.current`; it works only because `setPreviewStream` and `setIsPiPActive` land in the same batch. Preserve the deps array exactly rather than "fixing" it.
- `handleStartRecording` depends on the whole `config` object, so toggling any source tears down and re-binds the keydown listener. That is current behaviour; keep it.
- `startCountdown` reads `countdownValue` out of `getState()` inside its interval instead of holding it, and the PiP dimension fallback (`settings.width || 1920`) treats 0 and `undefined` alike.
- The PiP composite branch is spelled twice (`config.screenEnabled && config.webcamEnabled && …` at 446 and again at 518) with slightly different trailing conditions.
- `handleDownload` mutates `document.body` to trigger the download; the browser stub in `appHarness` exists for exactly that.

## Risks
The hard part is not the JSX, it is the ref graph. `compositorRef` is read by four concerns (preview effect, thumbnail capture, `stopAllStreams`, `handleStartRecording`) and `cancelledRef` by four more (`handleStartRecording` resets it, `handleCancelRecording` and the unmount effect set it, the recorder's `onStop` reads it) — split them across two hooks that each create their own ref and the post-cancel `onStop` test goes green while the app silently saves a discarded take. Both must be created in exactly one hook and passed by reference; a ref appended to a deps array is safe, a ref *recreated* per hook is a bug that no existing test will catch except by luck. Second, the unmount teardown is order-dependent (`cancelledRef` → duration interval → countdown interval → `recorder.dispose()` → `stopAllStreams()` → store reset) and reaches `stopAllStreams` through `stopAllStreamsRef` precisely so it does not close over a stale copy; if the cleanup moves into a hook, the ref indirection must move with it and the sync effect must still run *before* the cleanup effect is registered — the two unmount tests assert `dispose` once, three `track.stop()` calls, `vi.getTimerCount() === 0` and a store back at idle, and they will catch a reordering, but only if you keep them running under both `countdownSeconds: 3` and `countdownSeconds: 0`. Third, the recorder's six callbacks are captured *once*, at `createRecorder` time, closing over the `stopAllStreams` and `saveRecording` identities from the render that started the take; any change to how those callbacks are memoised changes which copy a late `onStop` runs — this is the one place where "same behaviour, different identity" is not true. Fourth, effect 3 reads two refs and one state slice with a one-entry deps array, and effect 6 reads `state` plus six callbacks; both must keep their arrays verbatim. Finally, the coverage floors leave one statement of slack: extracting nine components and seven hooks roughly doubles the function count, so any new file that ships without its own test file will fail `test:coverage` before a reviewer ever sees it.
