## Global constraints

- **No behaviour change.** The 10 test files in `src/store/` and `src/store/__tests__/` are **byte-unchanged** — not one import path. So are the 65 files that drive the store through `src/test/fixtures/projectStore.ts`. Any assertion change is a finding, not a fix. `git diff --stat main -- 'apps/artist/src/store/*.test.ts' 'apps/artist/src/store/__tests__/**'` must show **zero lines** across every commit in this series.
- **`projectStore.ts` stays the entry point and its public surface is identical**: `useEditorStore`, `DEFAULT_PROJECT_NAME`, `selectTimelineDuration`, `selectClipCount`, `selectSelectedClip`, `selectSelectedTrack`, `getClipsAtTime`, `getClipAtTime`, `getClipPosition`, and the re-export of `getSnapPoints`/`findNearestSnapPoint`/`wouldOverlap` from `./timelineSnapping` (comment included). Slices are **internal** — nothing outside `src/store/` may import one, and no slice is re-exported. Verify with `grep -rn "Slice'" apps/artist/src --include='*.ts*' | grep -v '^apps/artist/src/store/'` returning nothing.
- **State moves, never added.** Every state field keeps its initial value, spelled the same way (`new Set<string>()`, `DEFAULT_KEYFRAME_PANEL_STATE` by reference — *not* cloned), every action keeps its name, parameter list, optional parameters and return value, and `EditorState` in `store/types.ts` is **not edited**. Each slice declares its own shape as `Pick<EditorState, '…' | '…'>` in its own file, so `types.ts` remains the single declaration of the interface and no logic lands in a coverage-excluded file.
- **The history mechanism is one module.** `storeHistory.ts` holds `MAX_HISTORY_SIZE`, `getUndoableState` and `pushToHistory`, and every mutating slice imports `pushToHistory` from it. `pushToHistory` is never re-implemented, re-spelled or inlined; the 36 call sites keep their exact text, the three `skipHistory` ternaries included, and the three `get()`-then-bare-`set` actions keep reading their pre-change state from `get()`.
- **Zustand slice pattern.** Each slice is `export const createXSlice: StateCreator<EditorState, [], [], XSlice> = (set, get) => ({ … })`, composed in `projectStore.ts` as `create<EditorState>((...a) => ({ ...createProjectSlice(...a), … }))`. `set`'s partial is typed over the whole `EditorState`, so a slice action writing `project` and `history` type-checks without a cast; `create<EditorState>` refuses to compile if the composition is missing a field. **Omit `get` from the parameter list of any slice that does not use it** — `@typescript-eslint/no-unused-vars` is on and `lint` must be 0.
- **Cross-slice reads go through `get()` or the `state` argument of `set` — never through an import.** No slice file may import another slice file. This is not a rule to be careful about, it is a property of the design: the only imports a slice has are `zustand`, `./types`, the pure helper modules and `uuid`.
- **Indentation is preserved so the diff is provably a move.** Actions today sit at two spaces inside the store literal; written as `= (set, get) => ({` a slice creator puts them at two spaces as well. Every moved block must be **byte-identical**, comments and blank lines included. Each task verifies with the script in "Proving a move" below, and the commit is inspected with `git diff --color-moved=zebra`.
- **Coverage floors (99/98/93/98) hold every task and only go up.** This is a pure move: no new conditionals, so the **branch denominator must not change** — re-measure and compare `branches.total` against 4,292 (the current whole-package figure) and treat any change as a sign that something was rewritten rather than moved. The ~15 new slice-creator arrow functions all execute at store construction, so functions/lines/statements can only rise. Do not size headroom from the stale `coverage-summary.json` on disk.
- **Do not name any new file `types.ts`** (`apps/artist/vite.config.ts:160` excludes `**/types.ts` from coverage). New files go **flat in `src/store/`** next to `legacyOverlays.ts` and `timelineSnapping.ts` — no new directory, so no relative path in `src/store/__tests__/*.ts` (`'../projectStore'`, `'../types'`) shifts.
- ESLint's `ecmaVersion` here is **2020** (`apps/artist/eslint.config.js:19`): no `Array.prototype.at()`, no `??=`. Index from the end the way the original does (`newKeyframes[newKeyframes.length - 1]`, `clipIds[clipIds.length - 1]`).
- Files ≤ ~450 lines. `pnpm --filter @escapesuite/artist lint` 0 errors and no new warnings, `pnpm --filter @escapesuite/artist typecheck` (`tsc -b --noEmit`, tests included via `tsconfig.test.json`) clean, `pnpm --filter @escapesuite/artist test:coverage` green **per task**.
- **No new test files.** Unlike the component decompositions, every extracted module here is already exercised end-to-end by the 190 store tests through `useEditorStore` — a per-slice unit test would re-assert what `projectStore.test.ts` already asserts, against a slice that cannot be constructed without the composed state anyway. If a re-measure shows a metric *fell*, that is a finding about the move, not a licence to add tests. (Exception: if Task 1 leaves a pure helper with a branch no store test reaches, note it — do not "fix" it by changing the helper.)

## Open questions / rulings needed

1. **Do `legacyOverlays.ts` and `timelineSnapping.ts` move?** — **Recommend: no, neither.** Both are already extracted, already pure, already have their own byte-frozen test files, and both have importers outside the store (`headless/renderProject.ts:4` for the first; `components/Timeline/{useClipDrag,timelineGeometry}.ts` for the second). Moving either would break an import path for no gain. `projectStore.ts` keeps re-exporting the three snapping helpers even though no non-test caller uses that path today — it is public surface, and "identical afterwards" is the rule.
2. **Do the four `select*` selectors live beside a slice?** — **Recommend: they stay in `projectStore.ts`.** They are six lines of `(state: EditorState) => …` that read across slices (`selectSelectedClip` needs `project` *and* `selectedClipId`), so no slice owns them; `projectStore.test.ts:458–466` imports them from `'./projectStore'`; and a `store/selectors.ts` was deleted as dead in #355, so re-creating that filename would read as a revert. If a future need arises, the right home is `clipQueries.ts`, re-exported.
3. **Do the 23 `useEditorStore.setState(partial)` call sites in tests care about slicing?** — **No, and here is why.** Zustand keeps **one flat state object**; slices only change *where in the source the initializer literal is written*, never the shape of that object. `setState` does `Object.assign({}, state, partial)` (it is a shallow merge, `replace` defaulting to false), so `setState({ history: { past: [], future: [] } })` overwrites one key of the same flat object it always did, regardless of which file declared that key. The one thing that *would* break them is `setState(partial, true)` (replace), which no call site uses. The same argument covers `test/fixtures/projectStore.ts`'s `resetStoreForTest` and `useSessionAutosave.ts`'s `useEditorStore.subscribe` — a subscriber sees the whole state, not a slice.
4. **Flat `src/store/` or a new `src/store/slices/`?** — **Recommend flat.** `src/store/__tests__/*.ts` reaches the store as `'../projectStore'` and `'../types'`; a new directory does not break those, but flat keeps every relative path in the directory one shape, matches how `legacyOverlays.ts`/`timelineSnapping.ts` already sit, and keeps the vitest/coverage globs untouched. Fifteen new files in one directory is the cost; the `Slice` suffix keeps them scannable.
5. **Where does `keyframePanelState` live — `keyframeSlice` or `uiSlice`?** — **Recommend `keyframeSlice`.** It is panel UI, but it is *keyframe* panel UI, and the five setters read better beside the four keyframe-data actions than beside `setZoom`. `uiSlice` then holds exactly the five fields the original's "UI state" comment block names minus `markers` (its own slice) and minus the keyframe panel.
6. **Key order in the state object changes** — today all 22 state fields are declared first and the 66 actions after; with slices they interleave per slice. **Recommend accepting it.** Nothing iterates the store's own keys (`sameSourceVideo` iterates a `SourceVideo`, `buildSessionSnapshot` writes an explicit literal, every `toEqual` is order-insensitive), and the slices are composed in the original declaration order so the *relative* order of the fields is preserved anyway. Flag it here because it is the one observable difference in the composed object.
7. **New test files per slice?** — **Recommend none** (see Global constraints). The 190 store tests drive every action through `useEditorStore`, which is what a slice *is* once composed; a slice creator cannot meaningfully be exercised in isolation, and duplicating the suite would add functions to the coverage denominator for no new assertion. Revisit only if a re-measure shows a metric fell.
8. **Where does `recalculateTimelineDuration` go?** — **Recommend `clipSlice`.** It rewrites `timeline.duration` from the clips and is the only mutating action that touches neither `history` nor `modified`; that asymmetry is worth keeping visible next to the actions that do both.
9. **Should `MAX_HISTORY_SIZE` become an export of `storeHistory.ts`?** — **Recommend no.** It is module-private today and only `pushToHistory` reads it; `projectStore.test.ts`'s "drops the oldest snapshot once 50 are stored" asserts the literal 50 through behaviour, and `useKeyframeGraphKeyboard.ts:161` only names it in prose. Zero new exports is the cleaner invariant.
10. **Is `store/types.ts` (564 lines) in scope?** — **No.** It is types plus `DEFAULT_*` literals, coverage-excluded, and every slice's shape is expressed as `Pick<EditorState, …>` precisely so it need not be edited. A `types.ts` split is a separate decision with a separate risk (it is the file most imported in the app).
11. **Does anything in the plan touch `services/headless-artist`?** — **No.** It imports nothing from `projectStore`; the only cross-boundary dependency is `apps/artist/src/headless/renderProject.ts` → `store/legacyOverlays`, which does not move (Q1).
