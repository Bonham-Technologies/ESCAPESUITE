# Performance baseline — 2026-09-12

The first numbers `pnpm perf` produced, taken before any optimisation work on the
performance pass. Everything later in the pass is measured against this file.

Reproduce with:

```bash
pnpm perf
```

## What is measured

All three benchmarks run against **one deterministic scene**, built in-test from the
single fixture at `apps/e2e/fixtures/headless/source.mp4` (1 s, 64×48, H.264):

- 12 media clips, six per track across two video tracks. Track `V1`'s six run back to
  back from 0 s; track `V2`'s six are offset half a second and scaled to a rotating
  picture-in-picture box at 85% opacity, so every frame composites two decoded sources.
- Every fourth clip carries a 4 px blur, every fifth a `screen` blend mode.
- One 0.5 s `fade` transition on the third `V1` clip.
- One text overlay and one shape overlay, each on its own track, spanning the whole
  6.5 s timeline — 14 clips over 4 tracks at a 1280×720 project resolution.

Nothing in the scene varies by clock or random source, so two runs composite exactly
the same frames. It is loaded through the documented integration API — the fixture is
imported once through the media library's real file input, `GET_STATE` reports the id
that import was given, and `LOAD_PROJECT` installs a project whose clips reference it.
No app code exists for the benchmarks' sake.

| Benchmark | Window |
|-----------|--------|
| `preview-playback` | 6 s of playback, first 1 s discarded → a 5 s window |
| `export-mp4` / `export-webm` | One 720p export of the same scene, click to file |
| `headless-kit-render` | One `renderInChromium` call on `fixtures/headless/project.json`, Chromium launch included |

Each is run three times; wall-time metrics are reported as the median of the three.

## Where the numbers came from

| | |
|---|---|
| Machine | MacBook Pro, Intel Core i9-8950HK @ 2.90 GHz, 12 logical cores, 32 GB |
| OS | macOS 15.7.9 (darwin-x64) |
| Node | v26.7.0 |
| Playwright | 1.63.0 (bundled Chromium) |
| App under test | ESCAPEARTIST dev server (Vite), `http://localhost:5175` |
| Chromium launch args | `--enable-precise-memory-info --disable-gpu --autoplay-policy=no-user-gesture-required` |
| Headless kit launch args | `--autoplay-policy=no-user-gesture-required --disable-gpu` (the driver's own defaults) |

`--enable-precise-memory-info` is required: without it `performance.memory` is bucketed
to 100 KB and quantised over time, so a heap delta is noise. `--disable-gpu` forces
software rasterisation, which is what a CI runner has anyway and what the headless kit
renders under — it keeps a local number in the same ballpark as a CI one and takes GPU
driver differences out of the comparison.

## How to read these

**CI numbers are relative, not comparable to these.** The `perf` job runs on a shared
`ubuntu-latest` runner whose CPU allocation varies run to run and is slower than this
machine; expect materially different absolute values there. What is meaningful is the
movement of a CI number against other CI numbers on the same branch, and the movement of
a local number against this file on the same machine.

Run-to-run spread observed locally over four consecutive full `pnpm perf` runs (each of
which is itself the median of three; run 3 is the one tabulated above):

| Benchmark | Run 1 | Run 2 | Run 3 | Run 4 |
|-----------|-------|-------|-------|-------|
| `preview-playback` rendered fps | 49.81 | 51.22 | 50.66 | 50.08 |
| `export-mp4` frames/s | 90.19 | 87.37 | 98.44 | 86.51 |
| `export-webm` frames/s | 95.35 | 95.96 | 92.81 | 92.81 |
| `headless-kit-render` frames/s | 51.55 | 52.63 | 51.46 | 49.50 |

Playback is stable to roughly ±1.5 fps and the kit to ±2 frames/s; MP4 export throughput
swings about ±7%, so treat an export change smaller than that as noise. A *first* run
against a freshly started dev server measured 40.6 fps — Vite's on-demand transform of
the editor's modules competes with the first playback window — so `pnpm perf` is worth
running twice on a cold checkout and reading the second.

The headline the performance pass is aimed at: **the preview composites this scene at
~50 fps and spends ~600 ms of a 5 s window inside long tasks**, while the export path
puts the same 195 frames through in ~2 s.
