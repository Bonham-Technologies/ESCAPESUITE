# Performance baseline — 2026-09-12

The first numbers `pnpm perf` produced, taken before any optimisation work on the
performance pass. Everything later in the pass is measured against this file.

Reproduce with:

```bash
pnpm perf
```

## What is measured

All three benchmarks run against **one deterministic scene**, built in-test from the
single fixture at `apps/e2e/fixtures/headless/source.mp4` (1 s, 64×48, solid-red H.264):

- 12 media clips, six per track across two video tracks, two seconds each. Track `V1`'s
  six run back to back from 0 s; track `V2`'s six are offset a second and sit at a third
  of the scale as a rotating picture-in-picture box at 85% opacity, so every frame
  composites two sources.
- Clips are scaled to **fill the canvas**, not left at scale 1. Scale 1 means *native
  pixel size* in this editor, so a 64×48 clip at scale 1 would paint 0.3% of a 1280×720
  frame and the benchmark would measure the cost of compositing nothing.
- Every fourth clip carries a 4 px blur, every fifth a `screen` blend mode.
- One 0.5 s `fade` transition on the third `V1` clip.
- One text overlay and one shape overlay, each on its own track, spanning the whole
  **13 s** timeline — 14 clips over 4 tracks at a 1280×720 project resolution.

Nothing in the scene varies by clock or random source, so two runs composite exactly
the same frames. It is loaded through the documented integration API — the fixture is
imported once through the media library's real file input, `GET_STATE` reports the id
that import was given, and `LOAD_PROJECT` installs a project whose clips reference it.
No app code exists for the benchmarks' sake.

| Benchmark | Window |
|-----------|--------|
| `preview-playback` | 6 s of playback, first 1 s discarded → a 5 s window |
| `export-mp4` / `export-webm` | One 720p export of the same scene, click to file |
| `headless-kit-render` | One `renderInChromium` call on `fixtures/headless/project.json`, Chromium launch included |

Each is run three times; wall-time metrics are reported as the median of the three. The
13 s scene gives a ~6 s playback press better than 2× headroom, and `measurePlayback`
asserts the transport is still playing when the window closes, so a scene that ever
became too short fails loudly instead of reporting a frame rate averaged over a stretch
that was partly paused.

## Where the numbers came from

| | |
|---|---|
| Machine | MacBook Pro, Intel Core i9-8950HK @ 2.90 GHz, 12 logical cores, 32 GB |
| OS | macOS 15.7.9 (darwin-x64) |
| Node | v26.7.0 |
| Playwright | 1.63.0 (bundled Chromium) |
| App under test | ESCAPEARTIST dev server (Vite), `http://localhost:5175` |
| Chromium launch args | `--enable-precise-memory-info --disable-gpu --autoplay-policy=no-user-gesture-required` |
| Headless kit launch args | `--autoplay-policy=no-user-gesture-required --disable-gpu` (the driver's own defaults) |

`--enable-precise-memory-info` is required: without it `performance.memory` is bucketed
to 100 KB and quantised over time, so a heap delta is noise. `--disable-gpu` forces
software rasterisation, which is what a CI runner has anyway and what the headless kit
renders under — it keeps a local number in the same ballpark as a CI one and takes GPU
driver differences out of the comparison.

## How to read these

**These numbers weight compositing and encoding, not decoding.** The fixture is a 1 s,
64×48 clip upscaled to fill a 720p frame, so every decode is of a tiny picture and the
decoder is close to free. That is deliberate — it isolates the parts of the pipeline the
performance pass is aimed at — but it means a change to the decode path (the frame cache,
`videoDecodeManager`, `frameSource`) may barely move these figures while mattering a
great deal to a user working with real footage. Two related consequences:

- Chromium logs `WebCodecs failed … No keyframes found in video, falling back to
  HTMLVideoElement` for this fixture, so the exports here run through
  `HTMLVideoFrameSource`, not `WebCodecsFrameSource`. The WebCodecs decode path is
  **not** covered by these numbers.
- Clip durations (2 s) are longer than the 1 s source, so the second half of each clip
  holds the source's last frame. It composites and encodes exactly like any other frame;
  it simply asks nothing new of the decoder.

**Runs 2 and 3 of each benchmark are warm.** The three runs happen inside one page, so
run 1 pays for decoder set-up and a cold frame cache and runs 2–3 do not. The median of
three therefore leans warm by construction. It is the right number for comparing commits
— steady-state cost is what optimisation work moves — but it is not what a user's first
press of Play costs.

**CI numbers are relative, not comparable to these.** The `perf` job runs on a shared
`ubuntu-latest` runner whose CPU allocation varies run to run and is slower than this
machine; expect materially different absolute values there. What is meaningful is the
movement of a CI number against other CI numbers on the same branch, and the movement of
a local number against this file on the same machine.

Run-to-run spread observed locally over three consecutive full `pnpm perf` runs (each of
which is itself the median of three; run 3 is the one tabulated above):

| Benchmark | Run 1 | Run 2 | Run 3 |
|-----------|-------|-------|-------|
| `preview-playback` rendered fps | 50.16 | 49.52 | 49.05 |
| `export-mp4` frames/s | 77.49 | 77.63 | 77.17 |
| `export-webm` frames/s | 80.70 | 79.58 | 80.76 |
| `headless-kit-render` frames/s | 52.54 | 53.57 | 50.85 |

Tight: playback within ~1 fps, both exports within ~1.5%, the kit within ~3 frames/s
(its wall time is dominated by Chromium launch, which is the jumpiest part). Treat a
change smaller than those bands as noise.

The headline the performance pass is aimed at: **the preview composites this scene at
~49 fps and spends ~320 ms of a 5 s window inside long tasks**, while the export path
puts 390 frames through in ~5 s — roughly 2.5× real time.
