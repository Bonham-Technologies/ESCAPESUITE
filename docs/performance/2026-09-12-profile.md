# CPU profiles and hotspots — 2026-09-12

Where the time actually goes in ESCAPEARTIST's two hot paths — compositing the preview
during playback, and compositing plus encoding an MP4 export — measured with the
renderer's own sampling profiler against the
[baseline](2026-09-12-baseline.md)'s 14-clip scene.

**Nothing is fixed here.** This file's job is to say what is hot, why, and in what order
it is worth touching; the ranked list at the end is the input to the next task.

## How these were recorded

```bash
PERF_PROFILE=1 pnpm perf
```

`PERF_PROFILE=1` makes each browser benchmark run **one extra time**, and only that extra
run is profiled (`withCpuProfile` in `apps/e2e/utils/perf.ts`: CDP `Profiler.enable` →
`setSamplingInterval(100)` → `start` around the measured window → `stop` → `disable`). The
sampler perturbs exactly the timing the benchmarks report, so the medians in
`perf-report.json` are still taken from three unprofiled windows — the profiled run's own
measurement is discarded. The raw files land in `apps/e2e/perf-results/` (gitignored; also
uploaded by the CI `perf` job) and the `.cpuprofile` opens in Chrome DevTools' Performance
panel as-is:

| File | Window |
|------|--------|
| `preview.cpuprofile` | the 5 s playback window, warm-up excluded |
| `export-mp4.cpuprofile` | click on **Download MP4** to the file arriving |
| `export-webm.cpuprofile` | the same for WebM (not tabulated below; it is the MP4 shape with `exportToWebM` in place of `exportToMP4`) |
| `<name>.maps.json` | the source maps for every `/src/` module the profile sampled |

`apps/e2e/scripts/profile-top.mjs` turns a profile into the two tables below, and
`perf-report.mjs` embeds the same tables in the merged report when the files exist:

```bash
node apps/e2e/scripts/profile-top.mjs apps/e2e/perf-results/preview.cpuprofile
```

**Self time** is the sampler's own accounting — each interval charged to whatever was on
top of the stack. In the CDP format `timeDeltas[i]` is the interval *before* `samples[i]`,
so a sample is charged the interval that **follows** it and the last sample takes what is
left of the window; charging `timeDeltas[i]` to `samples[i]` would shift every microsecond
one sample early and credit each function's cost to whatever ran just before it.
**Total time** counts an interval once for every distinct function anywhere on that stack
(once, so recursion cannot multiply a total past the window), which makes a frame with no
self time but a large total a subsystem's entry point. `profile-top.test.mjs` pins both
rules, and the source-map lookup with them (`pnpm test:scripts`).

**Locations are source locations.** Vite's dev server hands the browser an
esbuild-transformed module, so the line numbers V8 records are lines of the *served* text,
not of the `.ts` file — `canvasRenderer.ts:238` in a raw profile is really line 310 on disk.
`withCpuProfile` therefore saves each module's inline source map beside the profile and
`profile-top.mjs` resolves every frame through it. A row that could not be resolved says
`(served)` and is a line in `node_modules/.vite/deps/…`, which is what it looks like.

`(program)`, `(idle)` and `(garbage collector)` are V8's synthetic frames, not code anyone
can edit. They are excluded from the percentage denominator — so "73% of self time" means
73% of *JavaScript execution*, not 73% of a window that was 20% idle between animation
frames — and reported separately underneath each table.

### Four things that shape every number below

1. **Main thread only.** The MP4 export decodes in a Web Worker with its own isolate. It
   does not appear here at all; what it costs shows up only as main-thread idle.
2. **Software rasterisation.** The perf project launches with `--disable-gpu`
   (see `PERF_LAUNCH_ARGS`), so every `drawImage` is rasterised on the CPU and lands in
   this profile. A user on a GPU-composited canvas pays much less for the same call — but
   a CI runner, a headless render box and a low-spec laptop are all closer to this than to
   a discrete GPU, and `services/headless-artist` renders under exactly these flags.
3. **A Vite dev server and a development React build.** `exports.jsxDEV`,
   `validateProperty` and `updatedAncestorInfoDev` are development-only overhead that a
   production bundle does not carry. **The render *count* is real; its unit price is not.**
   Where a React figure is quoted below, treat it as an upper bound and the count of
   renders as the durable finding.
4. **The fixture is tiny and the scene has no keyframes.** A 64×48 source upscaled 20× to
   fill the frame weights compositing and all but removes decoding, and every clip's
   transform is static — so anything whose cost scales with keyframe count (the animation
   engine, its cache) is measured at its floor here.

### What those entries are

**`drawImage` — 2571 ms self, 72.7%.** Not our JavaScript: the browser's rasteriser, charged
to the `ctx.drawImage(source, x, y, scaledWidth, scaledHeight)` at the bottom of
`drawClipToCanvas` (`apps/artist/src/core/canvasRenderer.ts:374`). Over the ~246 frames the
benchmark composited in that window that is **~10.4 ms of rasterisation per frame**, against
a 20 ms budget at 50 fps. Three things make it expensive, all visible in the scene: each
frame upscales the 64×48 source 20× to cover a 1280×720 canvas *and* draws the PiP clip over
it (two full filtered blits per frame); `ctx.filter = blur(4px)` on every fourth clip forces
the rasteriser into an offscreen layer plus a separable blur; and
`globalCompositeOperation: 'screen'` on every fifth takes it off the fast `source-over` path.
During the 0.5 s fade, `drawSide` (`canvasRenderer.ts:619`, 10.3% total) draws *both* sides of
the transition, doubling those frames' blits.

**React re-render — `performWorkOnRoot` 884 ms total, 25.0%** (`exports.jsxDEV` alone is
640 ms of self time, 18.1%). This is the second-biggest cost in the preview and it is
entirely avoidable work. `usePreviewRenderLoop`'s rAF loop (`animate`, resolved to
`usePreviewRenderLoop.ts:343`) calls `setDisplayTime(newTimelineTime)` **every animation
frame** (`usePreviewRenderLoop.ts:511`), which re-renders `PreviewPlayer` and its subtree 50
times a second so a timecode readout can change. The 248 layouts the same run records over
5 s are the same event — one layout per frame, for a text node. Inflated by the dev build,
but the 50 renders/s are real in production too.

> **Corrected 2026-09-12 (after round 1 — see the section at the end of this file).** The
> attribution above is wrong about *which* component pays the 640 ms. Task 1 removed exactly
> this per-frame `setDisplayTime` and re-measured on the same machine: `exports.jsxDEV`'s self
> time did not move (639.5 → 632.9 ms). The layout count did (247 → 63/64, real and durable),
> but the render-count story was one file short — `App.tsx` also subscribed to `currentTime`
> and re-rendered `<Timeline/>` regardless of what `Timeline` itself did, so the 640 ms tracked
> `Timeline` and `App` re-rendering on the throttled 200 ms `currentTime` write, not
> `PreviewPlayer`'s per-frame one. Task 3 fixed both subscriptions and `jsxDEV` fell to 116.7 ms
> (18.2% → 3.6%). Read "the preview subtree" below as "the whole editor tree below `App`", and
> read the 248-layout finding as the one part of this paragraph that held up unchanged.

**`Timeline` — 381 ms total, 10.8%.** The other half of the same story, one level up. The
loop also writes the playhead to the store every 200 ms (`setCurrentTime`, deliberately
throttled), and each of those ~25 writes re-renders the whole timeline — 14 clips, tracks,
ruler — at roughly 15 ms a render in this build. The throttle is why it is 10% and not 50%.

**`useStore` (zustand) — 11.1 ms self, 23.1 ms total, 0.3%.** Store reads themselves are
cheap. The cost of a store write is the React render it triggers, counted above, not the
subscription machinery.

**The app's own per-frame logic is invisible.** `animate` 3.8 ms self, `drawPreviewFrame`
1.9 ms, `getClipsAtTime` 1.6 ms, `drawClipToCanvas` 1.4 ms, `drawClip` 1.3 ms,
`getAnimatedValues` 0.7 ms — **under 11 ms of self time between them across the whole 5 s
window**, ~0.3% of JS. Per frame that is single-digit *micro*seconds. Whatever is worth
optimising in the preview, it is not the clip lookup or the animation evaluation.

**Row 2 of the total-time table is `drawFrame`.** The source map resolves it to
`PreviewPlayer.tsx:90` — the `useCallback` the rAF loop calls — which is worth naming
because it is also the identity that, if it ever changed per render, would tear the loop
down (see "Suspected but not visible").

**`(idle)` 1017 ms (19.8% of the window).** The rAF loop is not saturating the frame budget
outright — but `TaskDuration` for the same run says the renderer was busy 4278 ms of 5 s
(83%), and the preview lands at 49.3 fps rather than 60. Removing either of the two big
costs above should convert directly into frame rate.

**`(garbage collector)` 24 ms (0.5%).** Allocation pressure during playback is not a problem
in this scene. The 217 KB heap delta the same run reports agrees.

### What those entries are

**`drawImage` — 3196 ms self, 91.7%.** The export is one thing: rasterising frames. Over 390
frames that is **~8.2 ms per frame**, close to the preview's ~10.4 ms (the preview pays a
little more because it also draws selection chrome and waits on vsync). The call site is
identical — `drawClipToCanvas` at `canvasRenderer.ts:310` — which is the good news: **one fix
to the compositor moves both benchmarks.**

**`VideoFrame` — 77.1 ms self, 2.2%.** Constructing `VideoFrame`s to hand the encoder. Real,
unavoidable, and second on the list only because everything else is so small.

**`getFrame` — 8.9 ms self, 14.4 ms total** (`frameSource.ts:193`), with `onSeeked` at 7.4 ms
total. This is the whole decode-side cost visible on the main thread. The baseline explains
why it is so low: this fixture has no keyframes, so Chromium falls back to
`HTMLVideoFrameSource`, and the WebCodecs decode path is not exercised at all. **Do not read
"decoding is free" out of this profile** — read "decoding is absent from it".

**`animatedValuesFor` — 5.6 ms self, plus `getAnimatedValuesCached` 2.0 ms.** The animation
cache that never hits (below). 0.22% of the export's JavaScript. *(`getAnimatedValuesCached`
and the cache it read from were deleted in round 1, Task 5 — see "After round 1" — because a
memo keyed on a value that changes every frame cannot answer, ever, on either path. There is
now one entry point, `getAnimatedValues`, called unconditionally.)*

**React — 96.3 ms total, 2.8%**, essentially all `ExportDialog` repainting its progress bar.
Worth knowing, not worth chasing.

**`(garbage collector)` 15.2 ms (0.3%), heap delta 83 KB.** The export's frame loop is not
allocating its way into trouble either.

## What the profile says about the Task 2 findings

The unit-level ceilings (`*.perf.test.ts`) recorded three findings. The profile confirms all
three exist and **contradicts the implied priority of two of them**.

| Finding | Status in the profile |
|---|---|
| The exporter's animation cache never hits — keyed `` `${clip.id}:${clipTime}` ``, and every export frame has a fresh `clipTime` (`canvasRenderer.ts:35` in `animatedValuesFor`, and again at `exportMP4.ts:495`) | **Real, and ~0.22% of the export.** `animatedValuesFor` 5.6 ms plus `getAnimatedValuesCached` 2.0 ms, of 3485 ms. The cache costs a `toFixed(3)`, a string concat and a `Map.set` per clip per frame and returns a hit never; it also grows to its 10 000-entry cap and is then useless. Worth deleting as a *correctness* defect — a memo that cannot hit is a lie in the code — but nobody will see the milliseconds. Note the floor caveat: this scene has **no keyframes**, so the work the cache fails to avoid is at its cheapest here. |
| The preview composites twice per playhead move when two live clips share one source `<video>` (`usePreviewRenderLoop.ts:124–138`) | **Not visible, and it cannot be** — that seek-and-redraw effect begins `if (isPlaying) return;`. It is a *scrub* cost; the playback profile takes the rAF path and never enters it. Neither benchmark scrubs, so nothing here confirms or denies the size of it. It stands on the unit test alone. |
| CRAFT's compositor calls `restore()` twice per `save()` on the PiP frame | **Out of scope for these profiles entirely** — they profile ESCAPEARTIST. There is no CRAFT benchmark. An unbalanced context stack is a bug to fix on its own merits, not a performance item. |

*(All three fixed in round 1, Task 5 — the animation cache deleted, the shared-source seek
now once per element, CRAFT's compositor balanced. None moved a benchmark number, exactly as
this table predicted; see "After round 1".)*

The profile's own headline finding is one no unit test suggested: **the preview spends a
quarter of its JavaScript re-rendering React**, and none of it on the work the ceilings count.

## Suspected but not visible

Honest accounting of the things this pass expected to find and did not:

- **The `|| []` store selectors** (`PreviewPlayer.tsx:36–37`,
  `state.project.timeline.textOverlays || []`). The hazard is real — a selector that
  allocates a fresh `[]` per snapshot changes identity on every store read, which would
  re-create `drawFrame` (`PreviewPlayer.tsx:90`, whose deps include both overlay arrays),
  which would tear down and restart the rAF playback effect (`usePreviewRenderLoop.ts:533`
  lists `drawFrame` as a dep) on every render, re-seeking and re-`play()`ing every video.
  **It did not fire here**: both the default project (`projectStore.ts:105`) and the
  migration on load (`projectStore.ts:1618–1633`) guarantee the arrays exist, so `|| []`
  never allocates and the loop survived the whole window. It is a latent trap guarded by two
  invariants, not a live cost — but it is one selector edit away from being catastrophic,
  and cheap to make unconditionally safe.
- **`hitTest` / `contentBox` per-mouse-event allocations.** Zero samples: neither benchmark
  moves the pointer. Unmeasured, not disproved.
- **`drawSelectionHandles` allocations.** Nothing is selected in the perf scene, so the
  overlay returns early. Unmeasured.
- **`getClipsAtTime` filtering per frame.** Measured, and it is 1.6 ms across 5 s
  (~6 µs/frame). Not a candidate.
- **`getAnimatedValues` recomputed per preview frame** (the preview deliberately passes
  `uncachedAnimation`). 0.7 ms across 5 s. Not a candidate.

### What moved and what did not

**Transferable — real in a production build, not just this profile.** The preview's forced
layouts fell from 246 to ~66 across every resolution (Task 1's mechanism: the per-frame
`setDisplayTime` is gone, replaced by a ≤10 Hz publish/subscribe timecode). Long tasks went
from 6/9/22 (720p/1080p/4K) to **zero at all three**, and that is a main-thread stall a user
feels, independent of dev vs. production React. Most of all, `drawImage`'s cost is now
constant across project resolution — the backing store follows the displayed box, not
`project.resolution` — so a 4K project's preview went from 11.9 fps (worse than a slideshow)
to the same 60 fps ceiling as 720p. That mechanism (fewer pixels rasterised per frame) costs
exactly the same in a release build.

**Dev-build artefact — real today, overstated as a user-facing number.** `exports.jsxDEV`
(React's dev-mode JSX factory) does not exist in a production bundle. Its *share* of preview
JS looks similar before and after (18.1% → 21.1%), which could misread as "React got worse" —
what actually happened is the JS total it is a share of collapsed 85% (3535 ms → 520 ms), so
`jsxDEV`'s **absolute** cost fell from 639.5 ms to 109.9 ms even though its percentage rose.
Task 3's own before/after isolated this cleanly: fixing `Timeline`'s and `App`'s
`currentTime` subscriptions took `jsxDEV` from 640.8 ms (18.2%) to 116.7 ms (3.6%) with no
other change in flight, which is the strongest evidence that the 640 ms was never
`PreviewPlayer`'s per-frame render (Task 1's original target) — it was `Timeline` and `App`
re-rendering on the throttled 200 ms store write, and `PreviewPlayer` re-rendering per rAF
frame cost comparatively little on its own (Task 1 alone: +0.4–0.6 fps, inside the noise
band). The corrected causal story is in the "Corrected 2026-09-12" note earlier in this file.

### Follow-ups (not done in this round)

1. **Constant-screen-size selection handles.** Handles are still drawn at a fixed size in
   *project*-space pixels, so on a large project shown in a small box they are sub-pixel on
   screen — unchanged behaviour, deliberately, per the Task 4 brief. The fix is a one-liner at
   the draw site: divide the handle size by the frame's raster scale `k`, and match it in
   `hitTest`. (Task 4 report, §7.4)
2. **Frame-cache resize invalidation — dormant, not broken.** `core/frameCache.ts` entries are
   bitmaps captured at whatever backing-store size was current when they were made.
   `PreviewPlayer`'s cached-frame draw path already rescales a cached bitmap to the *current*
   backing size on every read (the same `setTransform` + `drawImage` at project size every
   other frame uses), so a resize never shows the wrong picture — at worst a softer one until
   the next fresh composite recaptures it at the new size. No invalidation-on-resize exists
   because none is needed for correctness, only for sharpness in that narrow window.
3. **DPR change without a resize.** `devicePixelRatio` is read at draw time, not subscribed
   to, so dragging the window to a different-DPI display re-rasterises only on the next
   resize or edit, not immediately. A `matchMedia('(resolution: Xdppx)')` listener is the
   usual fix; left out of Task 4 to keep that change to one idea. (Task 4 report, §7.3)
4. **Per-element seek winner — documented, not open.** The scrub seek check
   (`usePreviewRenderLoop.ts`) now seeks each `<video>` element at most once per pass instead
   of once per clip; when two live clips share one source, the later write wins and a
   transition's incoming side is applied last, reproducing the same visible frame the old
   per-clip loop produced. Documented in `apps/artist/CLAUDE.md`'s Preview section. (Task 5)
5. **The blur bitmap cache — ruled out, not deferred.** Candidate 3(b) above: blur is 30.6% of
   preview JS and 37.9% of MP4 export time in this scene, comfortably over the plan's 15%
   threshold for building a cache — but a frame-identity cache answers only on the benchmark
   fixture's frozen tail (a 44% "hit rate" that is an artifact of a 1 s source under 2 s
   clips, not a property of real footage) and is not pixel-identical for a rotated,
   fractionally-opaque draw (≤3/255 residual after the geometry is made exact). Task 4's
   raster fix cuts the same cost directly, by rasterising fewer pixels, with no cache and no
   pixel-fidelity question. Revisiting a cache would need `requestVideoFrameCallback` for real
   frame identity, a device-space cache key (the full CTM, not just source + time), and an
   explicit product ruling on whether a ≤3/255 shift on blurred pixels is within "no
   user-visible change." (Task 2 report, Part B)
