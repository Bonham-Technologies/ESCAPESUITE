# CPU profiles and hotspots — 2026-09-12

Where the time actually goes in ESCAPEARTIST's two hot paths — compositing the preview
during playback, and compositing plus encoding an MP4 export — measured with the
renderer's own sampling profiler against the
[baseline](2026-09-12-baseline.md)'s 14-clip scene.

**Nothing is fixed here.** This file's job is to say what is hot, why, and in what order
it is worth touching; the ranked list at the end is the input to the next task.

## How these were recorded

```bash
PERF_PROFILE=1 pnpm perf
```

`PERF_PROFILE=1` makes each browser benchmark run **one extra time**, and only that extra
run is profiled (`withCpuProfile` in `apps/e2e/utils/perf.ts`: CDP `Profiler.enable` →
`setSamplingInterval(100)` → `start` around the measured window → `stop` → `disable`). The
sampler perturbs exactly the timing the benchmarks report, so the medians in
`perf-report.json` are still taken from three unprofiled windows — the profiled run's own
measurement is discarded. The raw `.cpuprofile` files land in `apps/e2e/perf-results/`
(gitignored; also uploaded by the CI `perf` job) and open in Chrome DevTools' Performance
panel as-is:

| File | Window |
|------|--------|
| `preview.cpuprofile` | the 5 s playback window, warm-up excluded |
| `export-mp4.cpuprofile` | click on **Download MP4** to the file arriving |
| `export-webm.cpuprofile` | the same for WebM (not tabulated below; it is the MP4 shape with `exportToWebM` in place of `exportToMP4`) |

`apps/e2e/scripts/profile-top.mjs` turns one into the two tables below, and
`perf-report.mjs` embeds the same tables in the merged report when the files exist:

```bash
node apps/e2e/scripts/profile-top.mjs apps/e2e/perf-results/preview.cpuprofile
```

**Self time** is the sampler's own accounting — each interval charged to whatever was on
top of the stack. **Total time** counts an interval once for every distinct frame anywhere
on that stack, so a function with no self time but a large total is a subsystem's entry
point. `(program)`, `(idle)` and `(garbage collector)` are V8's synthetic frames; they are
excluded from the percentage denominator (so "73% of self time" means 73% of *JavaScript
execution*, not of a window that was 20% idle between animation frames) and reported
separately underneath each table.

### Four things that shape every number below

1. **Main thread only.** The MP4 export decodes in a Web Worker with its own isolate. It
   does not appear here at all; what it costs shows up only as main-thread idle.
2. **Software rasterisation.** The perf project launches with `--disable-gpu`
   (see `PERF_LAUNCH_ARGS`), so every `drawImage` is rasterised on the CPU and lands in
   this profile. A user on a GPU-composited canvas pays much less for the same call — but
   a CI runner, a headless render box and a low-spec laptop are all closer to this than to
   a discrete GPU, and `services/headless-artist` renders under exactly these flags.
3. **A Vite dev server and a development React build.** `exports.jsxDEV`,
   `validateProperty` and `updatedAncestorInfoDev` are development-only overhead that a
   production bundle does not carry. **The render *count* is real; its unit price is not.**
   Where a React figure is quoted below, treat it as an upper bound and the count of
   renders as the durable finding.
4. **The fixture is tiny and the scene has no keyframes.** A 64×48 source upscaled 20× to
   fill the frame weights compositing and all but removes decoding, and every clip's
   transform is static — so anything whose cost scales with keyframe count (the animation
   engine, its cache) is measured at its floor here.

### What those entries are

**`drawImage` — 2577 ms self, 73.1%.** Not our JavaScript: the browser's rasteriser, charged
to the `ctx.drawImage(source, x, y, scaledWidth, scaledHeight)` at the bottom of
`drawClipToCanvas` (`apps/artist/src/core/canvasRenderer.ts:374`). Over ~252 composited
frames that is **~10.3 ms of rasterisation per frame**, against a 20 ms budget at 50 fps.
Three things make it expensive, all visible in the scene: each frame upscales the 64×48
source 20× to cover a 1280×720 canvas *and* draws the PiP clip over it (two full filtered
blits per frame); `ctx.filter = blur(4px)` on every fourth clip forces the rasteriser into
an offscreen layer plus a separable blur; and `globalCompositeOperation: 'screen'` on every
fifth takes it off the fast `source-over` path. During the 0.5 s fade, `drawSide`
(10.7% total) draws *both* sides of the transition, doubling the frame's blits.

**React re-render — `performWorkOnRoot` 867 ms total, 24.6%** (`exports.jsxDEV` alone is
632 ms of self time, 17.9%). This is the second-biggest cost in the preview and it is
entirely avoidable work. `usePreviewRenderLoop`'s rAF loop calls
`setDisplayTime(newTimelineTime)` **every animation frame** (`usePreviewRenderLoop.ts:511`),
which re-renders `PreviewPlayer` and its subtree 50 times a second so a timecode readout can
change. The 253 layouts the baseline records over the same 5 s window are the same event —
one layout per frame, for a text node. Inflated by the dev build, but the 50 renders/s are
real in production too.

**`Timeline` — 368 ms total, 10.4%.** The other half of the same story, one level up. The
loop also writes the playhead to the store every 200 ms (`setCurrentTime`, deliberately
throttled), and each of those ~25 writes re-renders the whole timeline — 14 clips, tracks,
ruler — at roughly 15 ms a render in this build. The throttle is why it is 10% and not 50%.

**`useStore` (zustand) — 11.9 ms self, 24.1 ms total, 0.3%.** Store reads themselves are
cheap. The cost of a store write is the React render it triggers, counted above, not the
subscription machinery.

**The app's own per-frame logic is invisible.** `drawPreviewFrame` 3.7 ms self, `animate`
3.5 ms, `drawClip` 2.7 ms, `getClipsAtTime` 0.59 ms, `getAnimatedValues` 0.38 ms —
**under 12 ms of self time between them across the whole 5 s window**, ~0.3% of JS. Per
frame that is single-digit *micro*seconds. Whatever is worth optimising in the preview, it
is not the clip lookup or the animation evaluation.

**`(idle)` 1037 ms (20.3% of the window).** The rAF loop is not saturating the frame budget
outright — but `TaskDuration` in the baseline says the renderer was busy 83% of the wall
clock, and the preview lands at 50 fps rather than 60. Removing either of the two big costs
above should convert directly into frame rate.

**`(garbage collector)` 22 ms (0.4%).** Allocation pressure during playback is not a
problem in this scene. The 177 KB heap delta the baseline reports agrees.

### What those entries are

**`drawImage` — 3223 ms self, 92.0%.** The export is one thing: rasterising frames. Over 390
frames that is **~8.3 ms per frame**, the same per-frame cost as the preview's ~10.3 ms
(the preview pays a little more because it also draws selection chrome and waits on vsync).
The call site is identical — `drawClipToCanvas` — which is the good news: **one fix to the
compositor moves both benchmarks.**

**`VideoFrame` — 65.5 ms self, 1.9%.** Constructing `VideoFrame`s to hand the encoder. Real,
unavoidable, and second on the list only because everything else is so small.

**`getFrame` — 11.5 ms self, 18.6 ms total** (`frameSource.ts:105`), with `onSeeked` at
7.1 ms total. This is the whole decode-side cost visible on the main thread. The baseline
explains why it is so low: this fixture has no keyframes, so Chromium falls back to
`HTMLVideoFrameSource`, and the WebCodecs decode path is not exercised at all. **Do not read
"decoding is free" out of this profile** — read "decoding is absent from it".

**`animatedValuesFor` — 4.4 ms self, plus `getAnimatedValuesCached` 0.9 ms.** The animation
cache that never hits (below). 0.15% of the export's JavaScript.

**React — 94.6 ms total, 2.7%**, essentially all `ExportDialog` repainting its progress bar.
Worth knowing, not worth chasing.

**`(garbage collector)` 13.7 ms (0.3%), heap delta 60 KB.** The export's frame loop is not
allocating its way into trouble either.

## What the profile says about the Task 2 findings

The unit-level ceilings (`*.perf.test.ts`) recorded three findings. The profile confirms all
three exist and **contradicts the implied priority of two of them**.

| Finding | Status in the profile |
|---|---|
| The exporter's animation cache never hits — keyed `` `${clip.id}:${clipTime}` ``, and every export frame has a fresh `clipTime` (`canvasRenderer.ts` `animatedValuesFor`, and again at `exportMP4.ts:495`) | **Real, and ~0.15% of the export.** `animatedValuesFor` 4.4 ms of 3505 ms. The cache costs a `toFixed(3)`, a string concat and a `Map.set` per clip per frame and returns a hit never; it also grows to its 10 000-entry cap and is then useless. Worth deleting as a *correctness* defect — a memo that cannot hit is a lie in the code — but nobody will see the milliseconds. Note the floor caveat: this scene has **no keyframes**, so the work the cache fails to avoid is at its cheapest here. |
| The preview composites twice per playhead move when two live clips share one source `<video>` (`usePreviewRenderLoop.ts:124–138`) | **Not visible, and it cannot be** — that seek-and-redraw effect begins `if (isPlaying) return;`. It is a *scrub* cost; the playback profile takes the rAF path and never enters it. Neither benchmark scrubs, so nothing here confirms or denies the size of it. It stands on the unit test alone. |
| CRAFT's compositor calls `restore()` twice per `save()` on the PiP frame | **Out of scope for these profiles entirely** — they profile ESCAPEARTIST. There is no CRAFT benchmark. An unbalanced context stack is a bug to fix on its own merits, not a performance item. |

The profile's own headline finding is one no unit test suggested: **the preview spends a
quarter of its JavaScript re-rendering React**, and none of it on the work the ceilings
count.

## Suspected but not visible

Honest accounting of the things this pass expected to find and did not:

- **The `|| []` store selectors** (`PreviewPlayer.tsx:36–37`,
  `state.project.timeline.textOverlays || []`). The hazard is real — a selector that
  allocates a fresh `[]` per snapshot changes identity on every store read, which would
  re-create `drawFrame` (whose deps include both overlay arrays), which would tear down and
  restart the rAF playback effect (`usePreviewRenderLoop.ts:533` lists `drawFrame` as a dep)
  on every render, re-seeking and re-`play()`ing every video. **It did not fire here**: both
  the default project (`projectStore.ts:105`) and the migration on load
  (`projectStore.ts:1618–1633`) guarantee the arrays exist, so `|| []` never allocates and
  the loop survived the whole window. It is a latent trap guarded by two invariants, not a
  live cost — but it is one selector edit away from being catastrophic, and cheap to make
  unconditionally safe.
- **`hitTest` / `contentBox` per-mouse-event allocations.** Zero samples: neither benchmark
  moves the pointer. Unmeasured, not disproved.
- **`drawSelectionHandles` allocations.** Nothing is selected in the perf scene, so the
  overlay returns early. Unmeasured.
- **`getClipsAtTime` filtering per frame.** Measured, and it is 0.59 ms across 5 s
  (~2 µs/frame). Not a candidate.
- **`getAnimatedValues` recomputed per preview frame** (the preview deliberately passes
  `uncachedAnimation`). 0.38 ms across 5 s. Not a candidate.

## Ranked candidates for Task 4

Impact is quoted against the *measured* share of the profiled window, with the dev-build and
software-raster caveats above applied. "Both" means the change moves preview and export
together.

| # | Candidate | Where | Expected impact | Risk |
|---|---|---|---|---|
| 1 | **Rasterise the preview at display size, not project resolution.** The canvas backing store is always `project.resolution` (`PreviewPlayer.tsx` `canvasDimensions`) while CSS scales it to fit (`width:100%; object-fit:contain`) — so a 4K project rasterises 8.3 Mpx per frame into a ~600 px box. Size the backing store to the element's CSS box × `devicePixelRatio` and scale the context once. | preview | **Large.** Raster cost is area-proportional and `drawImage` is 73% of preview JS; at the benchmark's own geometry this is a ~2–3× cut in the dominant term. | **Medium-high.** `scaleX` is in *native source pixels*, so the whole scene must be drawn through one `ctx.scale(k, k)`; `previewGeometry`/`hitTest`/`selectionOverlay`/`frameCache` all read `canvas.width`. Needs a visual-regression pass. |
| 2 | **Stop re-rendering React every animation frame.** `setDisplayTime` per rAF (`usePreviewRenderLoop.ts:511`) drives 50 renders/s of the preview subtree; push the playhead through a ref and write the timecode readout directly (or throttle it to ~10 Hz). | preview | **Large.** 867 ms / 24.6% of preview JS today, and the 253 per-frame layouts with it. Production React is cheaper per render, so call it a solid 8–15% there — still second only to raster. | **Medium.** `displayTime` is consumed by the timecode and the transport; anything else reading it must be found. Purely additive to #1. |
| 3 | **Make the compositor's per-frame blits cheaper.** Two concrete sub-items: (a) skip or cache `ctx.filter = blur(...)` — it forces an offscreen layer per blurred clip per frame, and a clip whose blur and source frame are unchanged could reuse a cached bitmap; (b) give the preview canvas `{ alpha: false }`, which both exporters already use (`exportMP4.ts:147`, `exportWebM.ts:105`) and the preview does not (`PreviewPlayer.tsx:96`). | **both** | **Medium–large, and unmeasured.** `drawImage` is 73%/92% of the two windows, but the profile cannot attribute inside it — the split between upscale, blur and blend has to be found by ablation. Worth an experiment *before* committing to a design. | **Low** for (b); **medium** for (a) — a blur cache is new state with its own invalidation. |
| 4 | **Keep the store's 200 ms playhead write out of the timeline's render path.** ~25 writes over 5 s cost 368 ms of Timeline renders (10.4%). A transient subscription (or moving the playhead to a ref-driven element) removes them without changing the throttle. | preview | **Medium.** ~10% of preview JS in this build; more on a timeline with many clips, which is the case that already feels slow. | **Medium.** Timeline reads `currentTime` in several places; each has to be checked. |
| 5 | **Delete the exporter's animation memo cache (or key it so it can hit).** `animatedValuesFor`'s `` `${clip.id}:${clipTime.toFixed(3)}` `` is unique per frame by construction. | export | **Negligible measured (~0.15%)**, but it removes a string, a `Map.set` and a 10 000-entry cap per clip per frame, and the Task 2 test that pins the miss. Take it as cleanup riding along with a real change. | **Low.** Flip the ceiling test's assertion when it lands. |
| 6 | **Fix the double composite on a shared source element while scrubbing** (`usePreviewRenderLoop.ts:124–138`) and **CRAFT's unbalanced `save`/`restore`** in the PiP compositor. | scrub / CRAFT | **Unmeasured.** Neither is on a benchmarked path; both are defensible as correctness. | **Low.** Both are small, local, and already covered by a unit test that says what the right behaviour is. |

**Do not start with #5 or #6 because a unit test found them.** The profile is unambiguous
about where the milliseconds are: rasterisation first, React re-renders second, everything
the ceilings count third — by two orders of magnitude.
